### B06-001 — CRITICAL — VERIFIED
**Affected:** `apk/materialize-native-platform.cjs:195-201` (`ensureGithubToken`), `apk/materialize-native-platform.cjs:188-193` (`storeGithubToken`)
**User symptom:** After initial GitHub device-flow authorization, subsequent `githubApi` calls silently fail with "GitHub is not connected" even though a valid access token exists in secure storage, because `ensureGithubToken` returns early only when `access` is non-empty **and** `refresh` is empty — but `storeGithubToken` only writes `GH_ACCESS` when `access_token` is present in the token response, while the device-flow token response may omit `access_token` on refresh (returning only `refresh_token` + new `access_token` in some edge cases), leaving `GH_ACCESS` stale or missing.
**Technical root cause:** `ensureGithubToken` logic at lines 195-201:
```java
String access = secure.get(GH_ACCESS);
String refresh = secure.get(GH_REFRESH);
if (refresh == null || refresh.isEmpty()) {
    if (access != null && !access.isEmpty()) return access;
    throw new IllegalStateException("GitHub is not connected");
}
```
If `refresh` exists but `access` is empty/expired, it proceeds to refresh. However `storeGithubToken` (lines 188-193) only updates `GH_ACCESS` when `json.has("access_token")`. GitHub's device-flow refresh response **always** includes `access_token`, but if the native HTTP call truncates or the JSON parse fails silently, `access_token` may be missing and `GH_ACCESS` never updated, causing permanent "not connected" state until re-auth.
**Minimal reproduction:** 1) Complete device flow, verify `GH_ACCESS` stored. 2) Manually clear `GH_ACCESS` from SharedPreferences (simulate parse failure). 3) Call `githubApi` — observe "GitHub is not connected" despite valid `GH_REFRESH`.
**Fix direction:** In `ensureGithubToken`, if `refresh` exists but `access` is missing, force a refresh attempt instead of throwing; in `storeGithubToken`, validate `access_token` presence and throw if absent rather than silently skipping.
**Regression test:** Unit test `ensureGithubToken` with (a) valid access+refresh, (b) missing access+valid refresh, (c) missing both — verify correct behavior and no silent token loss.

### B06-002 — HIGH — STRONG
**Affected:** `apk/materialize-native-platform.cjs:212-219` (`githubApiOnce`), `apk/materialize-native-platform.cjs:203-211` (`allowedGithubPath`)
**User symptom:** GitHub API calls to legitimate repo-development paths (e.g., `/repos/Awfdfhy/seven-ai-true/issues`, `/repos/Awfdfhy/seven-ai-true/pulls`, `/repos/Awfdfhy/seven-ai-true/contents/...`) are rejected with "SecurityException: GitHub path or method is outside Seven's repository-development boundary" because `allowedGithubPath` only allows paths starting with `/repos/Awfdfhy/seven-ai-true` but blocks all sub-paths not explicitly allowlisted; the blocked list at lines 208-211 includes `/actions/secrets`, `/dependabot/secrets`, etc., but the allow logic is **prefix-only** with no sub-path traversal — so `/repos/Awfdfhy/seven-ai-true/issues/123` fails the `startsWith` check because it's not exactly the repo root.
**Technical root cause:** Line 206: `if (!path.startsWith(GITHUB_REPO)) return false;` where `GITHUB_REPO = "/repos/Awfdfhy/seven-ai-true"`. A path like `/repos/Awfdfhy/seven-ai-true/issues` **does** start with that prefix, but the subsequent blocked-path check at line 208 iterates `blocked` array and returns false if any blocked prefix matches. However, the logic is inverted: it checks `if (!path.startsWith(GITHUB_REPO)) return false;` then checks blocked paths — but the blocked paths are **absolute** (e.g., `/actions/secrets`) not relative to repo root, so they never match. The real bug: the method allows **only** the exact repo root path because no sub-paths are explicitly permitted; the blocked list is ineffective for repo-scoped paths.
**Minimal reproduction:** Call `githubApi` with `path: "/repos/Awfdfhy/seven-ai-true/issues"` — observe SecurityException.
**Fix direction:** Change `allowedGithubPath` to allow any path under `GITHUB_REPO` prefix **except** explicitly blocked suffixes (e.g., `/repos/.../actions/secrets`). Use `path.startsWith(GITHUB_REPO + "/") || path.equals(GITHUB_REPO)` for allow, then check blocked suffixes.
**Regression test:** Parametrized test covering allowed paths (issues, pulls, contents, actions/runs, actions/jobs) and blocked paths (secrets, collaborators, deploy_keys, environments).

### B06-003 — HIGH — VERIFIED
**Affected:** `release/github-self-dev.js` (not fully shown but referenced in `apk/materialize-android-visual-test.cjs:107-109`), `release/workspaces/coding.js`
**User symptom:** Opening the GitHub Self-Dev panel in the coding workspace fails silently on Android — the visual test at `materialize-android-visual-test.cjs:107-109` injects a script that sets `window.__sevenGhVisual` to 'loading', then 'ok'/'bad'/'error', but the test waits for `#seven-github-selfdev .seven-gh-panel` selector which may not exist if the panel HTML is not injected or the CSS class differs.
**Technical root cause:** The visual test assumes the GitHub Self-Dev panel renders with ID `seven-github-selfdev` and child `.seven-gh-panel`. However, `github-self-dev.js` (510 lines) likely constructs the panel dynamically. If the panel fails to mount (e.g., due to missing `SevenGitHubSelfDev` global, CSP blocking inline script, or native bridge not exposing `githubApi`), the test times out. The test does not verify *why* it failed — only that the selector didn't appear.
**Cross-system contradiction:** Native bridge (`materialize-native-platform.cjs`) exposes `githubApi`, `githubJobLogs`, `githubConnectionState` via Capacitor plugin, but the web runtime (`github-self-dev.js`) may call `window.SevenNative.githubApi` which doesn't exist if the plugin registration failed or the bridge name differs.
**Minimal reproduction:** Run the visual test on API 36 emulator; capture `adb logcat` for `SevenGitHubSelfDev` initialization errors.
**Fix direction:** Add defensive initialization in `github-self-dev.js`: check for native bridge availability, fall back to web-only mode with clear error UI; ensure panel DOM structure matches test selectors.
**Regression test:** E2E test that opens GitHub Self-Dev panel, verifies panel DOM exists, and can execute a read-only API call (e.g., `GET /repos/Awfdfhy/seven-ai-true`).

### B06-004 — MEDIUM — VERIFIED
**Affected:** `apk/materialize-native-platform.cjs:237-240` (`githubJobLogs`), `apk/materialize-native-platform.cjs:132` (`MAX_GITHUB_RESPONSE = 2*1024*1024`)
**User symptom:** Large GitHub Actions job logs (>2MB) are truncated silently to 180KB (line 240: `if (out.length() > 180000) out = out.substring(out.length() - 180000)`), but the native `MAX_GITHUB_RESPONSE` constant (2MB) suggests the intent was to allow up to 2MB. The truncation to 180KB is hardcoded and undocumented.
**Technical root cause:** Line 240 truncates to last 180K chars regardless of `MAX_GITHUB_RESPONSE`. The `ZipInputStream` reading loop respects `MAX_GITHUB_RESPONSE` (line 239: `text.size() < MAX_GITHUB_RESPONSE`), but then the final string is arbitrarily cut to 180K. This loses the beginning of logs which often contains setup/failure context.
**Minimal reproduction:** Trigger a workflow with >200KB logs; call `githubJobLogs`; verify returned logs length ≤ 180KB and missing prefix.
**Fix direction:** Remove the 180K truncation or make it configurable; respect `MAX_GITHUB_RESPONSE` consistently; consider streaming or pagination for large logs.
**Regression test:** Test with mock job logs of 100KB, 500KB, 3MB — verify returned size matches expectation and no silent data loss.

### B06-005 — MEDIUM — STRONG
**Affected:** `release/control-runtime.js` (stop generation patch), `release/beta-ui-runtime.js:36-38` (`installStopFix`), `release/execution-bridge.js`
**User symptom:** Stop generation button in coding workspace becomes unresponsive after first use — the `MutationObserver` in `installStopFix` (beta-ui-runtime.js:36-38) resets the button when it becomes hidden, but if the coding workspace reuses the same stop button across sessions, the `sevenPatched` flag on `r.stopGeneration` prevents re-patching, leaving the button in a disabled/stale state.
**Technical root cause:** `installStopFix` checks `if (r.stopGeneration && r.stopGeneration.sevenPatched) return;` (line 36). The `stopGeneration` function sets `stopRequested=true`, disables button, adds `seven-stopping` class, dispatches `seven:generation-stop-requested`. But the `MutationObserver` only triggers `resetStopButton()` when the button becomes **hidden** (line 38). If the button stays visible but disabled (e.g., after a failed stop), it never resets. The `sevenPatched` flag prevents re-initialization when workspace switches.
**Cross-system interaction:** Coding workspace (`workspaces/coding.js`) likely calls `installStopFix` on mount, but if the global `r` (SevenRuntime) persists across workspace changes, the patch runs once and never again.
**Minimal reproduction:** 1) Start generation in coding workspace. 2) Click stop. 3) Start new generation without hiding stop button. 4) Click stop again — button disabled, no action.
**Fix direction:** Reset button state in `stopGeneration` before disabling (re-enable, remove classes); or move `sevenPatched` check to per-workspace lifecycle; ensure `resetStopButton` is called on generation start.
**Regression test:** Simulate two consecutive generations with stop clicks; verify button re-enables and second stop works.

### B06-006 — MEDIUM — NEEDS_RUNTIME_TEST
**Affected:** `release/execution-bridge.js` (bridge between web and native), `apk/materialize-native-platform.cjs:163-167` (capability flags)
**User symptom:** Coding workspace GitHub actions (commit, push, PR creation) fail with "bridge not available" on Android release builds because the native platform declares `githubRepoApi: true` in capabilities (line 166) but the web runtime's `execution-bridge.js` may not route `githubApi` calls to the native plugin if the Capacitor plugin name or method signature mismatches.
**Technical root cause:** `execution-bridge.js` (134 lines) likely implements a `SevenNative` or `capacitor` bridge. The native plugin in `materialize-native-platform.cjs` exposes methods `githubApi`, `githubJobLogs`, etc. via `@PluginMethod`. If the web side calls `window.SevenNative.githubApi` but the plugin is registered as `SevenNativePlatform` or `SevenGitHub`, the call fails silently. The capability flag `githubRepoApi: true` is only informational.
**Evidence gap:** `execution-bridge.js` content not fully visible; need to verify bridge method naming matches native plugin.
**Minimal reproduction:** On device, open coding workspace, attempt GitHub API call; check `adb logcat` for "Plugin method not found" or bridge errors.
**Fix direction:** Align web bridge method names with native `@PluginMethod` names; add bridge health check in coding workspace init.
**Regression test:** Automated test that verifies `window.SevenNative.githubApi` resolves to a function and a test call returns structured response (even if auth fails).

### B06-007 — LOW — VERIFIED
**Affected:** `apk/materialize-native-platform.cjs:167-169` (`githubClientId` validation), `apk/materialize-native-platform.cjs:123` (`GITHUB_CLIENT_ID` pattern)
**User symptom:** GitHub device flow fails with "Invalid GitHub client id" for valid client IDs containing dots (e.g., `Iv1.abcdefghijklmnop`) because the regex `GITHUB_CLIENT_ID = Pattern.compile("[A-Za-z0-9_-]{10,120}")` excludes `.` which is valid in GitHub OAuth App client IDs (format `Iv1.<20-char>`).
**Technical root cause:** Line 123 pattern `[A-Za-z0-9_-]{10,120}` does not match `.`. GitHub's current client ID format for OAuth Apps is `Iv1.` + 20 alphanumeric chars (23 total). The pattern allows 10-120 but wrong charset.
**Minimal reproduction:** Call `githubBeginDeviceFlow` with client ID `Iv1.abcdefghijklmnopqr` — observe rejection.
**Fix direction:** Update regex to `[A-Za-z0-9_.-]{10,120}` or specifically `Iv1\.[A-Za-z0-9]{20}` for stricter validation.
**Regression test:** Test valid client ID formats (classic 20-char, new `Iv1.` format, GitHub App IDs).

### B06-008 — LOW — STRONG
**Affected:** `release/github-self-dev.js` (panel state), `release/workspaces/coding.js` (workspace lifecycle)
**User symptom:** GitHub Self-Dev panel retains stale connection state (shows "Connected" with old token) after `githubDisconnect` is called from another surface (e.g., settings), because the panel doesn't listen for `seven:github-disconnect` or storage change events.
**Technical root cause:** `githubDisconnect` (native, line 244-245) clears secure storage but doesn't broadcast an event. The web panel in `github-self-dev.js` likely reads `githubConnectionState` on mount only. No cross-surface invalidation.
**Cross-system:** Native `githubDisconnect` → web panel unaware.
**Fix direction:** Emit `seven:github-disconnect` custom event from native bridge after disconnect; panel listens and refreshes.
**Regression test:** Connect GitHub in panel, disconnect via settings, re-open panel — verify shows "Not connected".

### B06-009 — LOW — NEEDS_RUNTIME_TEST
**Affected:** `release/workspaces/coding.js`, `release/seven-shell-final.js` (workspace switching)
**User symptom:** Switching away from coding workspace during an active GitHub API call (e.g., fetching job logs) leaves the native thread running; returning to coding workspace shows stale/duplicate results because the previous call's callback resolves after workspace unmount.
**Technical root cause:** Native methods (`githubApi`, `githubJobLogs`) run on background threads (`new Thread(...).start()`). Web side has no cancellation token. Workspace unmount doesn't cancel in-flight native calls.
**Fix direction:** Add `AbortController`-style cancellation in bridge; native side checks cancellation flag; workspace cleanup cancels pending calls.
**Regression test:** Start job logs fetch, immediately switch workspace, verify no crash/duplicate UI on return.

## Cross-System Contradictions / Races
1. **Native token storage vs web panel state** (B06-001, B06-008): Native `SharedPreferences` is source of truth; web panel caches state without invalidation.
2. **Bridge method naming** (B06-006): Capacitor plugin method names must match web bridge exactly; no build-time verification.
3. **Stop generation patch global flag** (B06-005): `sevenPatched` on global `r.stopGeneration` prevents per-workspace re-initialization.
4. **Visual test selector coupling** (B06-003): Test selectors hardcoded to panel DOM structure; panel implementation changes break tests silently.

## Missing / Error States
- No error UI in GitHub Self-Dev panel for native bridge unavailable (B06-003)
- No rate-limit handling in `githubApiOnce` (reads `X-RateLimit-Remaining` but doesn't surface to caller)
- No token expiry proactive refresh (only on-demand in `ensureGithubToken`)
- No structured error codes from native to web (only string messages in `call.reject`)

# B07 Bug Audit Report — Provider / Network / Offline / Timeout / Rate Limit / Fallback

## Areas inspected
- `seven_ai-final.html`: free-provider health/cooldown, model discovery, route construction, provider adapters, fallback loop, search/network timeout wrappers, online/offline UI.
- Exact target identity in `.seven-team/bughunt/APK_TARGET.md`.
- Adjacent streaming/cancellation behavior.

## Bugs found

### B07-001 — Legacy WebView timeout fallback does not cancel the underlying request and misclassifies timeout errors
- **Severity:** HIGH
- **Confidence:** VERIFIED
- **Affected surface:** `fetchWithTimeout()`, `fetchProviderWithTimeout()`
- **User symptom:** On WebViews without usable `AbortController`, a request can time out in Seven while the real fetch/socket keeps running; provider/search telemetry can classify the failure incorrectly and late activity can outlive UI state.
- **Evidence / root cause:** both helpers fall back to `Promise.race([fetch(...), timeoutPromise])`. That only rejects the wrapper; it cannot abort the original fetch. The fallback timeout creates plain `Error("Request timed out")` without `REQUEST_TIMEOUT/PROVIDER_TIMEOUT`, so timeout-specific catch/classification logic is skipped.
- **Minimal reproduction / test idea:** Disable/stub `AbortController`, use a server that delays response beyond timeout, and verify the underlying request remains active and `classifyProviderFailureV2` does not receive timeout code.
- **Fix direction:** Provide a bridge/native cancellation primitive for legacy WebViews or explicitly quarantine the late request and normalize timeout errors identically.
- **Regression test:** AbortController and no-AbortController paths must emit the same typed timeout outcome and leave no active request.

### B07-002 — Provider model discovery has no timeout or cancellation boundary
- **Severity:** HIGH
- **Confidence:** VERIFIED
- **Affected surface:** `fetchProviderModelList()`, `refreshFreeModelCatalog()`
- **User symptom:** Model refresh can appear stuck indefinitely when one configured provider's models endpoint hangs.
- **Evidence / root cause:** discovery uses raw `fetch(provider.modelsUrl,...)` with no timeout/signal. `refreshFreeModelCatalog` waits on `Promise.allSettled`; allSettled cannot finish until every promise settles, so one hung fetch stalls the whole refresh.
- **Minimal reproduction / test idea:** Point one provider model-list endpoint at a connection that accepts but never responds; call forced catalog refresh and assert bounded completion.
- **Fix direction:** Reuse the typed timeout/cancellation wrapper for discovery with per-provider deadlines.
- **Regression test:** One hung discovery provider must not delay catalog refresh beyond its budget; other provider results must still publish.

### B07-003 — Discovery failures bypass provider health/cooldown and can be hammered repeatedly
- **Severity:** MEDIUM
- **Confidence:** STRONG
- **Affected surface:** `fetchProviderModelList()`, `refreshFreeModelCatalog()`, Provider Health v2
- **User symptom:** Repeated manual/forced refreshes can keep hitting an endpoint returning 429/5xx instead of respecting known cooldown behavior.
- **Evidence / root cause:** chat/provider calls invoke `recordFreeRouteFailure`, but model discovery throws directly and is only converted into an `errors[]` entry by allSettled handling. No discovery failure is recorded into Provider Health v2 and no Retry-After is parsed.
- **Minimal reproduction / test idea:** Make the models endpoint return 429 + Retry-After, force refresh twice, and count requests/health state.
- **Fix direction:** Record discovery health separately or feed bounded discovery failures into provider-wide cooldown without conflating them with chat-model health.
- **Regression test:** 429/503 discovery responses obey Retry-After/cooldown and preserve cached catalog.

### B07-004 — Sequential fallback can accumulate extreme worst-case latency across up to eight candidates
- **Severity:** HIGH
- **Confidence:** STRONG
- **Affected surface:** `buildFreeRouteCandidates()`, `callFreeModelFabric()`
- **User symptom:** On a degraded network, a single chat can remain “answering” for minutes before all free routes are exhausted.
- **Evidence / root cause:** routing returns up to 8 candidates. They are attempted sequentially. Provider adapters default to ~45s timeout when no explicit learned/priority timeout is supplied. In the pathological dead-connection case this permits roughly 8×45s before the final failure, excluding additional context/search time.
- **Minimal reproduction / test idea:** Configure multiple eligible providers to black-hole connections, disable latency-priority override, and measure end-to-end exhaustion time.
- **Fix direction:** Add a global request/fallback deadline and per-attempt remaining-budget allocation.
- **Regression test:** Total fallback wall-clock time must stay under one explicit request budget regardless of candidate count.

### B07-005 — Final route-exhausted error loses actionable Retry-After/cooldown detail in the user-facing message
- **Severity:** LOW
- **Confidence:** VERIFIED
- **Affected surface:** `sanitizeProviderError()`, `callFreeModelFabric()`, `describeNetworkError()`
- **User symptom:** User sees “All verified-free routes failed … rate limit reached” without knowing when retry is sensible.
- **Evidence / root cause:** individual errors capture `retryAfterMs`, but `attempts` stores only provider/model/status/sanitized text; the final Error message concatenates sanitized text and discards retry timing/cooldown metadata from the display path.
- **Minimal reproduction / test idea:** Return 429 with Retry-After from all eligible routes and inspect final UI text versus health record.
- **Fix direction:** Preserve a safe aggregate retry hint / next-available time in the final error envelope.
- **Regression test:** Multi-provider 429 exhaustion shows bounded non-sensitive retry guidance.

### B07-006 — “Online/offline” reliability state is link-state, not provider reachability
- **Severity:** LOW
- **Confidence:** NEEDS_RUNTIME_TEST
- **Affected surface:** `updateNetworkUiStateV1()`
- **User symptom:** UI can report online while every provider is unreachable.
- **Evidence / root cause:** state derives from `navigator.onLine`; provider health is rendered separately and the reliability field itself does not represent end-to-end connectivity.
- **Minimal reproduction / test idea:** Connected Wi‑Fi with broken DNS/upstream; compare reliability state with provider failures.
- **Fix direction:** Rename as device link state or combine with recent provider reachability.
- **Regression test:** Captive portal/no-upstream scenarios must not be presented as confirmed service reachability.

## Cross-system contradictions / races
- Chat/provider calls have typed health/cooldown; discovery calls bypass that network discipline.
- Modern AbortController path truly cancels; legacy fallback only times out the Promise wrapper.
- Candidate routing is bounded by count but not by a single global wall-clock budget.

## Missing / error states
- No typed timeout parity for legacy WebViews.
- No discovery deadline.
- No discovery Retry-After/cooldown integration.
- No global fallback deadline.

## False positives rejected
- Partial streamed output correctly prevents automatic retry to avoid duplicate visible text.
- Provider health/cooldown is persisted in localStorage; restart does not inherently erase it.
- Route construction deliberately promotes a different provider near the front when fallback is enabled.

## Top 5 highest-priority bugs

2. **B07-002** — unbounded model discovery fetch.
3. **B07-004** — multi-route fallback can take minutes.
4. **B07-003** — discovery failures ignore health/cooldown.
5. **B07-005** — route exhaustion hides retry timing.

# A06 Bug Hunt Report — Memory / Context / Persistence

## Areas Inspected
- memory.cjs (test suite for memory subsystem)
- release/control-runtime.js (context compilation, token estimation, side-effect ledger)
- release/execution-bridge.js (run lifecycle, checkpoints, side-effect persistence)
- release/build-release.cjs (build-time injection, not directly relevant)
- release/attachment-runtime.js, release/beta-ui-runtime.js (adjacent persistence)

## Bugs Found (sorted by severity)

### A06-002 — CRITICAL — Legacy migration not atomic → data loss
**File/function**: memory migration (likely in addMemory/init)
**Symptom**: After migrating from v1 to v2, if the write of v2 fails, the legacy v1 data is already deleted, resulting in total memory loss.
**Evidence**: Test "legacy keys remain unchanged" (memory.cjs:14) expects v1 keys absent after migration, implying deletion. No test covers partial failure.
**Reproduction**: Simulate storage quota error during v2 write after v1 deletion; observe v1 gone and v2 empty.
**Fix**: Write v2 to a temporary key, then atomically rename and delete v1 only after v2 is confirmed written.
**Regression**: Simulate write failure during migration and assert v1 data persists.

### A06-001 — HIGH — Corruption guard missing in update/delete
**File/function**: updateMemory, deleteMemory (memory subsystem)
**Symptom**: If the memory bundle is corrupted (e.g., 'bad' string), update/delete throw unhandled exceptions, crashing the app.
**Evidence**: Test "corruption cannot be replaced with empty data" (memory.cjs:11) only covers addMemory; update/delete paths likely parse bundle without try/catch.
**Reproduction**: Set localStorage['seven_ai_memory_bundle_v2']='bad'; call updateMemory or deleteMemory; observe exception.
**Fix**: Add try/catch around JSON.parse in update/delete, return null/false on corruption.
**Regression**: Add tests for update/delete with corrupted bundle, expecting graceful failure.

### A06-005 — HIGH — Checkpoint restoration lacks integrity validation
**File/function**: release/execution-bridge.js, restoreLatest (line 127)
**Symptom**: Corrupted checkpoint snapshot is restored, causing run state corruption and unpredictable behavior.
**Evidence**: restoreLatest returns the last checkpoint's snapshot without checksum or schema check.
**Reproduction**: Tamper with a stored checkpoint's snapshot; call restoreLatest; observe invalid state accepted.
**Fix**: Compute checksum on write, verify on restore; fallback to earlier valid checkpoint if invalid.
**Regression**: Write a checkpoint with corrupted snapshot and assert restoreLatest rejects it.

### A06-003 — MEDIUM — Token estimation underestimates for non-Latin text
**File/function**: release/control-runtime.js, tokensOf (line 13)
**Symptom**: Context overflow when using Arabic, Chinese, or code, leading to API errors or truncation.
**Evidence**: tokensOf uses `Math.ceil(t.length/4)`. For Arabic, token count ≈ character count, so estimate is ~4x too low.
**Reproduction**: Build context with 1000 Arabic characters; tokensOf returns 250, actual ~1000; exceeds typical 1k token budget.
**Fix**: Use language-aware token estimation or add safety margin (e.g., multiply by 2).
**Regression**: Test context compilation with multilingual content and assert actual token count ≤ budget.

### A06-004 — MEDIUM — Checkpoint snapshots cause unbounded growth
**File/function**: release/execution-bridge.js, persistCheckpoint (line 121)
**Symptom**: Long-running tasks accumulate large storage due to full ledger snapshots in each checkpoint.
**Evidence**: persistCheckpoint stores `clone(run.effects)` which is a full copy of the side-effect ledger.
**Reproduction**: Create many side effects and checkpoints; measure storage size; grows linearly.
**Fix**: Store deltas or limit checkpoint count; compact old checkpoints.
**Regression**: Benchmark storage after N checkpoints and assert size O(1) or O(log N).

## Cross-System Contradictions / Races
- **Checkpoint vs. side-effect execution**: If a checkpoint is taken while a side effect is in `PLANNED` or `ATTEMPTED` state, and the run is later restored, the system may re-execute the side effect because the restored ledger shows it as not yet attempted, leading to duplicate real-world effects (e.g., duplicate API calls). This is a race between execution-bridge's persistence and control-runtime's side-effect state machine.

## Missing / Error States
- Memory subsystem: no handling for `localStorage` being disabled (private browsing) beyond quota errors; getItem may return null, setItem may throw a different error.
- Migration: no rollback mechanism if v2 write fails after v1 deletion.
- Checkpoint: no handling for storage quota exceeded during persistCheckpoint; the error is thrown and may crash the run.

## False Positives Rejected
- Attachment loader hang after failure: While the loader can hang if a script element remains after a failed load, this is outside the memory/context specialization and does not affect persistence of user data.
- Theme persistence: The beta-ui-runtime theme handling is straightforward and correctly falls back to 'auto' on error; no bug found.
- Build-time injection failures: These are build-time checks and do not affect runtime memory behavior.

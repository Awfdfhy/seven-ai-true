# A02 Bug Audit Report — Android Lifecycle / Install-Upgrade / WebView / Native Boundary

## Areas Inspected
- Exact target identity in `.seven-team/bughunt/APK_TARGET.md` (Capacitor `ai.seven.v243`, Seven 2.4.3).
- `seven_ai-final.html`: IndexedDB room persistence, lifecycle/reliability hooks, network state, VisualViewport and generation cancellation.
- Android-sensitive boundaries: background/process death, resume, storage upgrade/blocking, Stop/cancellation.

## Bugs Found — Sorted by Severity

### A02-001 — IndexedDB startup/upgrade failure can leave the whole app permanently inert
- **Severity:** CRITICAL
- **Confidence:** STRONG
- **Affected surface:** `seven_ai-final.html` — `roomPersistence.init()`
- **User-visible symptom:** Seven can open with the entire UI unable to receive clicks or keyboard input after a storage open/upgrade failure.
- **Evidence / root cause:** initialization sets `document.body.inert = true` before opening IndexedDB. The success path clears it after the canonical room record is loaded, but the catch path only sets `failed=true` and shows “Storage unavailable or invalid…”; it does not restore `document.body.inert=false`. `request.onblocked` also rejects into this path.
- **Minimal reproduction / deterministic test idea:** stub `indexedDB.open` to reject or trigger `onblocked`; await initialization; assert that an actionable recovery UI remains interactive and `document.body.inert === false`.
- **Fix direction:** always leave a bounded interactive recovery state after storage failure; provide retry/export/recovery controls.
- **Regression test:** denied IndexedDB, blocked version upgrade, malformed legacy data, and transaction/open failure must never leave the full document inert.

### A02-002 — Android background/process death can race queued room persistence
- **Severity:** HIGH
- **Confidence:** STRONG
- **Affected surface:** `roomPersistence.save()/flush()`, `initAppReliabilityV1()`
- **User-visible symptom:** the newest acknowledged chat state can disappear if Seven is backgrounded and Android terminates the WebView before the queued IndexedDB write finishes.
- **Evidence / root cause:** room saves are serialized asynchronously through a Promise queue. The only unload guard is `beforeunload`. Production source contains no `pagehide` or `freeze` handler and no background lifecycle call to `roomPersistence.flush()`; `flush()` is used by explicit backup export instead.
- **Minimal reproduction / deterministic test idea:** delay the IDB transaction, perform a state-changing chat action, immediately background/terminate the WebView, relaunch, and compare the committed revision.
- **Fix direction:** add a best-effort persistence checkpoint for page/native backgrounding and expose unsaved state explicitly.
- **Regression test:** delayed-write + background/process-kill test must either preserve the last acknowledged state or visibly mark it unsaved before transition.

### A02-003 — Native Capacitor resume/app-state events are not proven wired to the Web runtime
- **Severity:** MEDIUM
- **Confidence:** NEEDS_RUNTIME_TEST
- **Affected surface:** `initAppReliabilityV1()`, Android lifecycle integration
- **User-visible symptom:** route status, viewport sizing, or room UI may remain stale after returning from a document picker, permission screen, or OS background transition.
- **Evidence / root cause:** the audited Web runtime synchronizes on `visibilitychange` and `pageshow`. No `Capacitor.App.addListener`, `appStateChange`, or equivalent native resume hook is present in the inspected production HTML. The APK target is a Capacitor app, so native lifecycle delivery must be verified separately.
- **Minimal reproduction / deterministic test idea:** on an Android emulator/device, exercise home→resume, permission/settings→resume, document picker→resume and rotation; assert `lastResumeAt`, viewport CSS variables, room UI and route status refresh.
- **Fix direction:** feed native app-state/resume events into the same idempotent resume synchronizer.
- **Regression test:** device/emulator lifecycle suite across pause/resume, chooser, permission, rotation and process recreation.

### A02-004 — Stop implementation contradicts its own mobile-WebView cancellation policy
- **Severity:** MEDIUM
- **Confidence:** NEEDS_RUNTIME_TEST
- **Affected surface:** `stopGeneration()`
- **User-visible symptom:** on affected mobile WebViews, pressing Stop may still trigger AbortSignal/bridge errors or unreliable cancellation behavior.
- **Evidence / root cause:** the inline comment states that Seven uses a stop flag “instead of calling AbortController.abort()” because some mobile WebViews can throw an AbortSignal clone error; the executable code immediately sets the flag and then calls `activeAbortController.abort()` inside a try/catch.
- **Minimal reproduction / deterministic test idea:** stop during search, provider request and streaming on multiple Android System WebView versions while capturing Web/native errors and request lifetime.
- **Fix direction:** make the policy internally consistent: use capability/bridge-specific cancellation where safe, otherwise flag-and-discard with bounded request cleanup.
- **Regression test:** Stop must terminate user-visible generation cleanly without bridge errors on supported Android/WebView versions.

### A02-005 — Reliability “online” state is derived from link status, not usable Internet reachability
- **Severity:** LOW
- **Confidence:** NEEDS_RUNTIME_TEST
- **Affected surface:** `updateNetworkUiStateV1()`
- **User-visible symptom:** Seven may report “online” while Wi-Fi is connected but DNS/upstream Internet/provider access is unavailable.
- **Evidence / root cause:** app reliability state is populated from `navigator.onLine` and online/offline events; no reachability probe participates in that field.
- **Minimal reproduction / deterministic test idea:** connect to a captive portal or Wi-Fi with no upstream route and compare `SevenAppReliability.snapshot().network` with actual provider reachability.
- **Fix direction:** label this value as link state or combine it with recent end-to-end reachability evidence.
- **Regression test:** airplane mode, captive portal, broken DNS and connected-without-Internet cases.

## Cross-System Contradictions / Races
- Canonical room persistence is asynchronous, but Android backgrounding has no matching persistence checkpoint.
- A generic resume abstraction exists, while native Capacitor lifecycle wiring is not established by the audited Web source.
- The documented Stop strategy and executable AbortController behavior disagree.

## Missing / Error States
- No explicit interactive recovery transition after IndexedDB startup failure.
- No `pagehide`/`freeze` persistence checkpoint in the inspected runtime.
- No native app-state hook proven in the audited Web layer.

## False Positives Rejected
- VisualViewport resize/scroll handling exists; it is not reported as broken without device evidence.
- File-input use alone is not treated as an Android permission bug.
- No claim is made here about manifest/exported-component/mixed-content settings because those were not proven by the inspected evidence.

## Top 5 Highest-Priority Bugs
1. **A02-001** — app-wide inert lock after storage/upgrade failure.
2. **A02-002** — queued persistence can race Android process death.
3. **A02-003** — native resume/app-state integration requires runtime verification.
4. **A02-004** — contradictory mobile cancellation implementation.
5. **A02-005** — link-state can be presented as connectivity state.

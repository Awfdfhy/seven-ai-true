# Seven Coding System — Deep Research Synthesis

Date: 2026-10-05
Status: research complete for architecture baseline; implementation evidence is tracked separately.

## Goal

Build a Coding Agent that can complete repository-level software engineering work through the full loop:

`Understand -> Inspect -> Research -> Plan -> Edit -> Test -> Debug -> Verify -> Review -> Document`

The target is not a text-to-code feature. The target is a controlled software-engineering runtime that can inspect real repository state, make bounded changes, execute verification, recover from failures, prove what happened, and stop safely when evidence is insufficient.

## Systems reviewed

### OpenAI Codex

Current Codex architecture emphasizes a bounded execution environment, workspace-scoped writes, network policy, approval boundaries, telemetry, code review, and test execution. OpenAI's 2026 engineering guidance explicitly combines sandboxing with approvals and agent-native audit logs. OpenAI also describes an internal development loop where agents self-review, request additional independent agent reviews, consume feedback, and repeat until reviewers are satisfied.

Sources:
- https://openai.com/index/running-codex-safely/
- https://openai.com/index/unrolling-the-codex-agent-loop/
- https://openai.com/index/harness-engineering/
- https://openai.com/index/introducing-upgrades-to-codex/

Seven should copy the architectural ideas, not product-specific implementation details: hard sandbox boundaries, separate policy from reasoning, proof-carrying completion, independent review, and explicit network/write scopes.

### Claude Code

Claude Code exposes repository reads, edits, shell execution, MCP integration, resumable sessions, bounded turn counts, explicit allow/deny tool rules, and a plan permission mode. Its security documentation treats read access differently from mutating actions and confines writes to project scope unless explicitly expanded.

Sources:
- https://docs.anthropic.com/en/docs/claude-code/cli-usage
- https://docs.anthropic.com/en/docs/claude-code/security

Seven should preserve the distinction between read-only investigation and mutating execution. Permission expansion must be a policy decision, never a model assertion.

### Cursor Agent / Cloud Agents

Cursor's current Agent architecture is explicitly composed of instructions, tools, and model. Plan Mode first researches the codebase and produces a reviewable implementation plan before building. Cloud Agents run in isolated VMs, can install/run/test software, and attach logs/screenshots/artifacts as proof.

Sources:
- https://prod.cursor.com/docs/agent/overview
- https://prod.cursor.com/docs/agent/plan-mode
- https://prod.cursor.com/help/ai-features/background-agents

Seven should separate planning from mutation for complex tasks and make execution artifacts first-class evidence.

### GitHub Copilot coding/custom agents

GitHub supports repository-level custom instructions, path-specific instructions, AGENTS.md, custom agents with scoped tools, MCP servers, and sub-agent orchestration. Built-in exploration and research roles demonstrate the value of specialized, restricted contexts.

Sources:
- https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-custom-agents
- https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents
- https://docs.github.com/en/copilot/how-tos/copilot-in-your-ide/customize-copilot/configure-custom-instructions/add-repository-instructions-in-your-ide

Seven should ingest repository instructions as policy/context and support specialized reviewer/researcher roles without letting sub-agents inherit unbounded authority.

### Gemini CLI

Gemini CLI provides an explicit policy engine with `allow`, `deny`, and `ask_user`, rule priority, plan-mode restrictions, sandboxing, workspace path controls, network controls, and sandbox expansion requests. Plan Mode is intentionally read-only.

Sources:
- https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/policy-engine.md
- https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/sandbox.md
- https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/plan-mode.md

Seven should treat permission decisions as deterministic policy evaluation and keep plan/research execution read-only by construction.

### OpenHands

OpenHands separates the reasoning-action loop, tool orchestration, context management, and security analysis. Its runtime model uses isolated workspaces/sandboxes and typed action/observation flows.

Sources:
- https://github.com/OpenHands/docs/blob/main/sdk/arch/agent.mdx
- https://github.com/OpenHands/docs/blob/main/openhands/usage/architecture/runtime.mdx

Seven should retain a small agent loop while putting complex guarantees in the runtime around it: workspace, policy, evidence, and verification.

### Aider

Aider's repository map extracts important symbols/signatures and ranks them by repository dependency relationships to fit a token budget. It can lint/test after edits and repair failures. Architect mode separates reasoning about the change from production of exact edits.

Sources:
- https://aider.chat/docs/repomap.html
- https://aider.chat/docs/usage/lint-test.html
- https://aider.chat/docs/usage/modes.html

Seven should build a token-budgeted repo intelligence layer, but the map must remain localization evidence rather than source truth. Exact source content must be re-read immediately before a mutation.

### mini-SWE-agent / SWE-agent lessons

The current mini-SWE-agent demonstrates that a very small model-facing loop can still be highly competitive: bash-only execution, linear history, and independent commands make the harness easier to debug and sandbox. This argues against unnecessary agent-scaffold complexity.

Sources:
- https://github.com/SWE-agent/mini-swe-agent
- https://mini-swe-agent.com/latest/

Seven should keep the model-facing tool surface small. Rich behavior belongs in deterministic adapters and policies, not dozens of bespoke prompts/tools.

### Cline

Cline exposes Plan/Act modes, MCP, workspace checkpoints/undo, sub-agents/teams, live terminal execution, compiler/linter feedback, and reviewable diffs.

Source:
- https://github.com/cline/cline

Seven should make rollback/checkpoints native, not an afterthought, and should preserve observable terminal/test feedback in the run record.

### OpenCode

OpenCode separates Build/Plan/Explore roles and supports resource-level allow/ask/deny permissions. It demonstrates a clean model where a reviewer or explorer can be genuinely read-only.

Sources:
- https://opencode.ai/v2/docs/agents
- https://opencode.ai/v2/docs/permissions

Seven should support role-specific capabilities while keeping the parent authority ceiling intact.

## Evaluation research that changes the design

### SWE-Touch: evolving workspaces are a first-class failure mode

SWE-Touch reports substantial degradation when user counter-edits occur during coding-agent work. The core lesson is that a plan tied only to a task description is unsafe; a plan must be tied to exact repository state, and the agent must re-inspect/reconcile when that state changes.

Design consequence for Seven: exact base commit SHA + source-file fingerprints + candidate workspace fingerprint are mandatory. A stale plan must fail closed. Silent overwrite of concurrent edits is forbidden.

### SWE-Bench / SWE-Bench Pro: benchmark PASS is not enough

SWE-bench Verified was useful but is now known to have contamination/saturation problems, and SWE-Bench Pro itself has had task-quality concerns. SWE-Bench Pro Verified specifically addresses reward hacking and flawed tasks.

Sources:
- https://www.swebench.com/verified.html
- https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/
- https://openai.com/index/separating-signal-from-noise-coding-evaluations/
- https://arxiv.org/abs/2609.08149

Design consequence for Seven: evaluation must include adversarial local cases, hidden/locked evaluators, stale-state cases, rollback cases, and real product build gates. No single public benchmark can be the acceptance criterion.

## Comparison: Seven before this campaign

### Strong existing foundations

Seven Remake V3 already has a mature Tool Fabric:
- versioned tool registry and strict schemas;
- scoped ToolGrant authority;
- ReferenceMonitor policy checks;
- exact invocation fingerprints and one-shot approvals;
- replay/effect ledger with `effect_unknown` handling;
- cancellation/deadline handling through TaskManager;
- bounded outputs and audit evidence;
- MCP adapter foundation;
- GitHub authentication/self-development service with base SHA in the change-set contract.

Seven also has older coding/evolution safety primitives:
- candidate isolation expectations;
- stable-head drift checks;
- bounded repair attempts;
- regression and independent review hooks;
- trusted evaluation bundles and promotion gates.

### Critical gaps

Before Coding System V1 there is no single product runtime that supplies all of the following together:
1. exact repository snapshot and workspace fingerprint;
2. stale-plan rejection at mutation time;
3. source-file hash preconditions;
4. transactional multi-file patch application with rollback evidence;
5. repo-map/symbol/dependency intelligence for localization;
6. deterministic test selection that the model cannot weaken;
7. real file/shell sandbox adapters owned by Tools;
8. git diff inspection as a mandatory stage;
9. evidence bundle binding plan, files, tests, diff, review and commit SHA;
10. full coding lifecycle state machine integrated with Seven task execution;
11. adversarial eval corpus for concurrent edits, evaluator tampering and rollback;
12. independent reviewer capability separated from the editor's authority/context.

## Architecture principles selected for Seven

1. **Workspace truth before reasoning.** Repository state is identified by exact commit SHA plus normalized file fingerprints.
2. **Read-only planning.** Understand/Inspect/Research/Plan cannot mutate the workspace.
3. **Small model-facing loop.** The model reasons; deterministic runtimes enforce policy, transactions, tests and evidence.
4. **Fail closed on drift.** Head drift, file drift, ambiguous anchors, unknown verification coverage, or uncertain side effects cannot silently become PASS.
5. **Transactional edits.** A multi-file plan either validates as a whole or does not apply. Rollback material is created before mutation.
6. **Blast-radius budgets.** File count, byte volume, path sensitivity and dependency scope are bounded before execution.
7. **Mandatory tests are policy-owned.** The model may add tests; it cannot remove required gates.
8. **Verification is separate from implementation.** Green tests are necessary but insufficient. Diff review, contract checks and independent review remain separate stages.
9. **Untrusted outputs stay untrusted.** Repository text, web results, tool output and generated test text do not grant authority.
10. **Evidence-carrying completion.** COMPLETE requires exact evidence; missing proof results in BLOCKED/INCONCLUSIVE, not optimistic PASS.
11. **Concurrency-aware.** Any workspace change after planning invalidates the affected plan until re-inspected.
12. **Recoverable by design.** Every mutation path has a rollback/checkpoint story before execution.
13. **Repository instructions are scoped context, not authority.** AGENTS.md/project rules can guide style/build commands but cannot override higher-level safety or integration contracts.
14. **Independent review gets less authority than editing.** Reviewer agents are read-only by default.
15. **No hidden contract mutation.** Changes to `docs/seven-master/INTEGRATION_CONTRACTS.md` require external authority, ADR documentation and integration verification.

## Selected target loop

`UNDERSTAND -> INSPECT -> RESEARCH -> PLAN -> EDIT -> TEST -> DEBUG* -> VERIFY -> REVIEW -> DOCUMENT -> COMPLETE`

`DEBUG*` is entered only after failed tests/verification/review and is bounded by repair budgets. Any phase may terminate as BLOCKED or FAILED with evidence.

This loop is deliberately more explicit than a generic ReAct loop because repository mutation requires stronger invariants than ordinary tool use.

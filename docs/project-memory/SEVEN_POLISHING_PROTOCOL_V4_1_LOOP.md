# Seven Polishing Protocol V4.1 — The Loop

Status: SELF-POLISH CANDIDATE
Parent: Seven Polishing Protocol V4
Purpose: extend V4 with benchmark-governed comparison, visual evidence, executable regression growth and self-polish recursion while preserving V4's bounded-saturation laws.

## Name
**The Loop**

`Polish → Measure → Challenge → Learn → Re-polish → Saturate`

## Prime rule
V4.1 inherits every V4 safety, authority, evidence, mobile, reality, uncertainty, regression, Pareto and saturation law, then adds:

> When a material claim is meaningfully measurable, the polishing decision must use a precommitted comparable BenchmarkContract or explicitly record why valid measurement is unavailable.

Benchmark results are evidence, not authority. They cannot compensate for C0 failure or silently override known correctness, security, data-integrity, accessibility or release blockers.

## The Loop law
A polishing protocol may polish its own successor, but the candidate may not move its own goalposts after observing results.

Self-polish cycle:
1. Lock parent protocol identity.
2. Lock BenchmarkContract / critical gates / resource envelope / visible-vs-holdout split.
3. Build successor candidate using the parent protocol.
4. Benchmark and challenge candidate against parent.
5. Integrate only material improvements.
6. Promote discovered material failures into permanent regression cases when testable.
7. Re-run applicable gates.
8. Reset saturation to 0/2 after any material improvement.
9. Stop only after complete eligibility + two valid clean challenge reviews.

No infinite recursion is required. The successor is evaluated as an artifact under a bounded campaign. Recursive polishing continues only when it produces material information gain.

## Anti-self-deception rules
- Candidate may not weaken already-locked C0/C1 gates after seeing results.
- Candidate may not delete an inconvenient benchmark without a documented invalidation reason.
- Benchmark code/config/evaluator changes are versioned and included in baseline identity.
- Improvements discovered by the candidate against itself require independent corroboration when the decision is material.
- Hidden/holdout cases remain unavailable to candidate tuning where practical.
- A new protocol version does not become canonical merely because it contains more mechanisms.
- Simplification can defeat the successor.

## V4.1 campaign phases
V4.1 preserves V4 Phases 0-23 and inserts executable evidence at the appropriate points rather than adding ceremony for its own sake.

### Phase 0 — Ground truth + identity lock
Lock exact parent/baseline/candidate context. For visual campaigns include build/commit/theme/locale/window/device/font-scale identities.

### Phase 1 — Domain discovery
Discover measurable and non-measurable dimensions separately. Do not force fake metrics onto subjective qualities.

### Phase 2 — Scenario utility tree
Each important scenario marks candidate evidence channels and criticality.

### Phase 3 — Research evidence
Use current official/platform/research evidence to inform metrics and failure surfaces. Time-sensitive benchmark assumptions receive freshness triggers.

### Phase 4 — First-principles candidate
Build strongest minimal design independent of current benchmark implementation.

### Phase 5 — Alternative tournament
Candidates compete on precommitted scenarios and metrics. Benchmark cost itself is part of complexity/resource tradeoff.

### Phase 6 — Builder review
Maximize useful capability.

### Phase 7 — Failure review
Failures become benchmark/regression candidates.

### Phase 8 — Simplifier review
Attempt to delete benchmark machinery that adds ceremony without discriminating useful candidates.

### Phase 9 — Unknown-unknown hunt
Seek unmeasured qualities, Goodhart effects, blind spots, evaluator bias, stale goldens, hidden environment dependence and benchmark gaming.

### Phase 10 — Cross-system shadow test
Check benchmark collection itself does not violate privacy, authority, startup, storage, battery or project boundaries.

### Phase 11 — Reality gate
Measurement must be implementable with available platform/runtime primitives. Mark unavailable evidence honestly.

### Phase 12 — Mobile physics gate
Measure on realistic Android tiers when the claim is mobile/device-level. Host or emulator evidence remains lower-tier.

### Phase 13 — UX/accessibility/visual gate
Use both structural and visual evidence where applicable. Visual evidence is mandatory for material appearance claims when capture is feasible.

### Phase 14 — Precommit BenchmarkContract
Before candidate comparison lock metrics, gates, baseline, repetitions, environment, acceptance and visible/holdout split.

### Phase 15 — Long-horizon/composition gauntlet
Run performance/reliability/composition cases at meaningful scale. Capture visual states at selected transitions rather than every frame by default.

### Phase 16 — Regression cemetery
Promote reproducible material counterexamples into permanent benchmark cases/invariants.

### Phase 17 — Pareto/tradeoff/sensitivity
Analyze metric sensitivity and variance. No universal scalar score hides regressions.

### Phase 18 — Proof of improvement
Every measurable material claim includes comparable result references. Non-measurable claims include rubric/reviewer evidence plus uncertainty.

### Phase 19 — Test derivation
Translate accepted properties into executable tests/benchmarks where feasible.

### Phase 20 — Reconciliation
Update protocol, benchmark contracts, regressions and evidence lineage together.

### Phase 21 — Independent challenge A
Attack architecture, measurement validity, benchmark gaming and simplification.

### Phase 22 — Independent challenge B
Use a materially different lens/evidence order/scenario family. Re-check whether the benchmark itself is hiding weaknesses.

### Phase 23 — Saturation freeze
Requires V4 eligibility plus applicable BenchmarkContract completion. 2/2 remains only the final bounded gate.

## Visual UI benchmark protocol
For UI/UX/Brand/Motion campaigns:
1. define journey/state matrix;
2. capture approved baseline/reference evidence where useful;
3. inspect source semantics/layout/accessibility data;
4. run deterministic visual diff where appropriate;
5. invoke multimodal visual inspection for semantic/aesthetic anomalies;
6. preserve disagreements between structural and visual channels;
7. test Day/Night, Arabic/RTL, mixed bidi, font scaling, reduced motion and representative screen classes using risk-based selection;
8. use frame/runtime metrics for smoothness, never infer FPS/jank solely from a still screenshot;
9. require representative real-device evidence before device-level release claims.

## Visual evaluator policy
A visual evaluator records:
- evaluator identity/version
- input artifact hashes
- rubric version
- structured observations
- uncertainty
- evidence dependencies

Changing evaluator/model/rubric invalidates cached judgments where material.

## Benchmark cost governor
Benchmarking must not become its own meteorite. Use staged escalation:
1. cheap deterministic/static checks
2. focused unit/property/replay checks
3. host benchmark / screenshot diff
4. multimodal visual review
5. emulator/instrumented run
6. representative device/release build
7. expensive long-horizon/holdout only when decision value justifies cost

C0/C1 evidence needs override cost-saving when required.

## Goodhart defense
If a metric becomes a target, actively search for cases where optimizing it harms the underlying quality. Maintain multiple orthogonal measures and qualitative/counterexample review for high-impact decisions.

## Benchmark invalidation
A benchmark result is not timeless. Invalidate/re-run when material identity changes include code, model/provider, evaluator, device/OS, build mode, benchmark implementation, schema, dataset/case set, resource envelope or platform behavior.

## Reopen triggers
All V4 triggers plus:
- benchmark detects material regression
- benchmark methodology is shown invalid
- evaluator drift/model change
- visual golden/reference proven stale
- new device/window/locale/accessibility failure
- evidence tier previously used is insufficient for a stronger claim
- benchmark gaming/Goodhart counterexample

## Canonical adoption rule
V4.1 becomes canonical only after it is itself polished under the parent V4/V4.1 Loop, passes applicable benchmark/visual/reality/mobile gates, and reaches a valid bounded 2/2 saturation. Until then V4 remains the canonical fallback.

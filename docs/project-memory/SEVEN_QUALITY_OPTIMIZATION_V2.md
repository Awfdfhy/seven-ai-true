# Seven Quality Optimization 2.0

Status: ARCHITECTURE_ACCEPTED

This is a reusable quality-improvement framework for Seven. It does not claim runtime implementation or measured performance gains.

## Ten refinement layers
1. Causal evidence: link each proposed change to its expected mechanism and measured outcome.
2. Typed change surfaces: evaluate prompts, routing, memory, tools, algorithms, UX, resources and code under appropriate separate criteria.
3. Reproducible evaluation package: lock requirements, evaluator versions, benchmark identities, environment and scoring rules before comparison.
4. Attribution checks: when practical, compare with and without the proposed change so gains are not assigned to the wrong cause.
5. Longitudinal pathway checks: verify that retained experience is saved, retrieved, applied, updated and forgotten as intended.
6. Evaluator calibration: prefer deterministic checks where applicable and use independent semantic judgment only where needed. Version and calibrate evaluators.
7. Diverse candidate archive: retain multiple alternative designs, including simpler ones, and compare them across multiple axes rather than one universal score.
8. Transfer checks: distinguish narrow benchmark wins from improvements that hold on adjacent unseen scenarios.
9. Improvement economics: include evaluation time, runtime cost, RAM, battery, storage and maintenance complexity in promotion decisions.
10. Governance separation: keep authoritative requirements, evaluation rules, evidence lineage, rollback and final promotion outside the candidate being evaluated.

## Materiality rule
The requested 200% rule is interpreted rigorously. Literal 2x claims are allowed only on ratio metrics where that statement is mathematically meaningful. Other qualities require a demonstrated categorical capability jump or substantial multi-axis improvement without forbidden regression.

## Iteration rule
A campaign may contain up to ten promoted refinement generations. It stops early when no qualifying improvement is demonstrated. Each later generation receives stronger relevant evaluation coverage. Ten is a ceiling, not a quota.

## Polishing integration
This framework is intended to become the common substrate for a future Polishing revision, combined with the existing Velocity, Maximum Research, visual/motion, benchmark and freeze rules. The existing V4.4 protocol remains canonical until a successor is separately validated and frozen.

## Evidence boundary
ARCHITECTURE_ACCEPTED does not mean IMPLEMENTED, TESTED, DEVICE_VERIFIED or RELEASE_PROVEN.

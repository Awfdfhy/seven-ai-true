# Seven AI — Context-Adaptive Maximum Effort Command Protocol

> **Status:** PROJECT-WIDE EXECUTION CONSTITUTION
> **Scope:** Every substantial Seven architecture, implementation, research, polish, repair, evaluation and visual-design step.

## Purpose
There is no magic phrase that increases capability. Maximum Effort means converting the exact task into a precise evidence-driven execution contract, using the strongest relevant research, reasoning, engineering, adversarial challenge, verification and preservation workflow available for that domain.

The protocol is itself improvable. When a material weakness is discovered, strengthen the protocol and reset any saturation evidence whose validity depended on the older constitution.

## Mandatory Preflight
Before substantial work:
1. identify exact goal, scope and non-goals;
2. reconstruct current repository/implementation truth before proposing replacement;
3. identify authoritative project decisions and protected invariants;
4. identify evidence and external research needed;
5. generate a context-specific Maximum Effort Command;
6. define falsifiable success/failure criteria and evidence classes;
7. identify mobile/performance and speed/smoothness budgets;
8. identify rollback/recovery and protected side effects;
9. execute, challenge, verify and preserve results in GitHub Project Memory.

## The Maximum Effort Envelope
Use the relevant dimensions at maximum practical depth.

### Research
- broad discovery before narrowing
- primary/current sources first when freshness matters
- multiple independent evidence classes where useful
- obscure credible alternatives, not popularity-only search
- counterexamples, failure reports and negative evidence
- contamination/search-exposure awareness for research-capable evaluators
- practical saturation rather than arbitrary result counts

### Reasoning
- decompose the problem and expose assumptions
- distinguish FACT / CLAIM / INFERENCE / PROPOSAL / UNKNOWN / CONFLICT
- compare strongest competing architectures
- search for hidden dependencies and second-order effects
- challenge the preferred design
- use counterfactuals/ablations where they can establish causality
- optimize Seven as a whole, not a subsystem in isolation

### Engineering
- inspect existing implementation first
- preserve mature systems
- define contracts, schemas, state transitions and invariants
- account for cancellation, retry, idempotency, permissions, lineage, verification, recovery and observability where relevant
- account for migration/backwards compatibility
- prefer simplification when capability is preserved
- do not confuse architecture documents with runtime implementation

### Speeding & Smoothness ⚡
Every substantial capability pass asks how to make the system faster and smoother without weakening truth or safety:
- cold/warm startup and time-to-interactive
- time-to-first-useful-result and end-to-end latency
- tail latency, jank and frame stability
- input/cancellation responsiveness
- scheduling/concurrency/critical-path optimization
- redundant calls/work elimination
- caching with correct freshness/authority/identity boundaries
- lazy/progressive loading
- progressive rendering/results where truthful
- RAM/allocation pressure
- network/storage round trips
- background wakeups/work
- CPU/thermal/battery cost
- performance-tier behavior

**Speed law:** remove waste, not required proof. Never trade away correctness, verification, authority boundaries, accessibility, recovery or canon fidelity for a flattering benchmark.

### Mobile / Android
- RAM and CPU
- battery and thermal pressure
- storage/APK size
- network use
- startup
- constrained-device behavior
- touch ergonomics
- Reduced Motion and performance tiers
- lazy/on-demand heavy systems

### Verification
- precommit success metrics where practical
- intended behavior plus important failure paths
- verify side effects rather than trusting reported success
- compare before/after
- use fresh/hidden or transfer evidence when public benchmarks can be gamed
- judge tail failures, not only averages
- rerun invalidated evidence after material changes
- no PASS from persuasive narrative or visual appearance alone

### Security / Integrity
- least authority
- explicit permissions
- protected destructive actions
- source integrity
- side-effect uncertainty
- rollback/recovery
- no authority escalation through derived data/model/tool echo
- privacy boundaries for screenshots, telemetry and visual evidence

### UX / Visual Intelligence
When user-facing:
- clarity and low friction
- recognizable Seven Design Genome
- phone ergonomics
- Day/Night
- Arabic/RTL/bidi
- accessibility, contrast, touch targets and focus
- Reduced Motion
- semantic motion
- typed/generated UI safety
- visual evidence from real renders
- distinctiveness/anti-copy checks
- performance cost of effects
- no visual state that falsely implies verification

### Preservation
Preserve materially relevant commands, sources, evidence, candidates, comparisons, rejected alternatives, assumptions, unknowns, architecture, decisions, implementation plan, tests/evals, results, remaining gaps and freeze criteria.

## Capability-Level Double-Polish Rule
Every canonical capability in `SEVEN_CAPABILITIES_MAP.md`, including Tool Fabric 2.0 capabilities, is eligible for two independent Maximum Effort polish passes.

**Pass A:** build the strongest evidence-supported candidate from the current state.

**Pass B:** attack the strengthened candidate from a fresh adversarial angle, searching for material gaps, simplification and performance gains.

Pass B is not required to produce changes. `NO_MATERIAL_IMPROVEMENT` is a valid and desirable result when justified. Never create ceremonial complexity to satisfy a two-pass ritual.

## Context-Adaptive Command Template
> **SEVEN MAXIMUM EFFORT — [EXACT STEP]**
>
> **Goal:** [precise measurable outcome].
>
> Reconstruct the current Seven state and authoritative decisions before changing anything. Preserve mature systems and protected invariants. Use the maximum practical depth of research, reasoning, competing-design comparison, engineering and verification relevant to this exact task. Search broadly where external evidence can materially improve the decision, prioritize primary/current evidence, and actively seek counterexamples, failure reports and stronger alternatives until practical saturation or a documented evidence gap.
>
> Separate verified fact from claim, inference, proposal, unknown and conflict. Do not invent capabilities or claim implementation/completeness without evidence. Analyze interfaces, dependencies, failure modes, security/permissions, side effects, recovery, observability, maintainability and migration wherever relevant.
>
> Apply the Seven Speeding & Smoothness System: inspect critical-path latency, startup, responsiveness, redundant work, scheduling, concurrency, caching, progressive/lazy loading, RAM/CPU/battery/thermal/network/storage cost and tail behavior. Remove waste without weakening required correctness, proof, authority, accessibility or recovery.
>
> Challenge the strongest candidate before accepting it. Run a Simplifier Duel against unnecessary complexity. Define falsifiable success criteria, evaluation evidence and freeze/saturation conditions. Do not declare PASS from appearance or narrative confidence.
>
> Preserve material research, decisions, rejected alternatives, specifications, evidence references, evaluation criteria and unresolved gaps in GitHub Project Memory in the same work cycle.
>
> **Domain-specific attack surface:** [generated uniquely for this step].

## Domain Mutation Examples
- **Tools:** capability coverage, contracts, schemas, permissions, side effects, idempotency, MCP/interoperability, reliability, adapter drift, latency and lazy discovery.
- **Memory:** authority, temporal/causal retrieval, consolidation errors, privacy, provenance, reconstruction and retrieval evals.
- **Coding:** project understanding, transactional edits, selective tests, repair loops, checkpoints, destructive-operation safety and time-to-verified-fix.
- **RPG/Real Works:** canon provenance, timeline/state, character knowledge, insertion constraints, divergence, CANON_GAP and continuity validation.
- **Visual/UI:** real scenario matrix, Design Genome, tokens/lint, logo/icon masks, real screenshots, accessibility, motion, RTL, Android performance, privacy and distinctiveness.
- **Models:** capability evidence, free-status proof, context limits, provider dialects, fallback, latency, routing and task-specific evals.
- **Research:** source identity, freshness, contradiction, retraction/correction, search exposure, citation integrity and evidence synthesis.

## Anti-Patterns
Do not use arbitrary counts as proof, popularity as quality, one benchmark as universal evidence, feature count as polish score, architecture that ignores the repository, claims of searching the entire internet, fake percentage gains, mean-only success, PASS without verification, or conversation memory as the only durable record.

## Completion / Saturation
A step completes only when its success criteria are met or blockers are explicitly documented. A capability freezes only after relevant architecture, behavior, failure handling, performance, verification and UX gates pass. Two consecutive valid no-material-improvement challenges may establish saturation for the tested scope. Any material change to the governing constitution or target can invalidate that evidence.

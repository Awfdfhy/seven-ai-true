# Seven Self-Evolution + General Improvement Integration

Status: ARCHITECTURE_CANDIDATE

## Goal
Use the General Improvement Engine as the governed development laboratory behind Seven Self-Evolution without allowing the system being improved to control the constitution that judges it.

## Separation of powers
### Builder Plane
May:
- inspect authorized architecture/code/eval summaries
- research alternatives
- generate candidate changes
- propose experiments
- request debugging/repair
- learn from released evidence summaries

May not:
- reveal future hidden holdouts
- rewrite authoritative requirements
- weaken C0/C1 gates
- change Promotion Gate thresholds after results
- suppress failed evidence
- self-authorize side effects
- self-promote

### Challenger / Judge Plane
Evaluates candidates against locked criteria, counterexamples, holdouts, transfer cases and regression protections. Judge identity/version is recorded and itself periodically calibrated.

### Promotion Plane
Owns final acceptance, lineage sealing, rollback references and release boundaries. Promotion authority is not delegated to Builder output.

## Improvement lifecycle
Weakness/opportunity detected
→ ImprovementTarget created
→ evidence/research collected
→ candidate families generated
→ causal hypotheses declared
→ evaluation package frozen
→ candidate tournament
→ adversarial/holdout/transfer evaluation
→ Debugging & Repair if needed
→ independent Judge
→ Promotion Gate
→ promoted version or reject/stop
→ learning ledger updated

## Recursive campaign
A Self-Evolution campaign may request up to 10 promoted generations from the General Improvement Engine. Each promoted generation receives a harder valid HostilityProfile. A generation is earned only by a qualifying step-change under the 200% Materiality class. If none survives, stop with NO_QUALIFYING_EVOLUTION.

The campaign is not required to produce ten versions. Ten is a ceiling.

## What can be improved
Subject to target authority and permissions:
- architecture and state models
- routing/model selection strategies
- memory/context algorithms
- tool planning/discovery strategies
- retrieval/research strategies
- coding workflows
- evaluator tooling
- debugging/repair strategies
- UI/UX systems
- performance/resource strategies
- prompts/policies that are not constitutional authority
- benchmark infrastructure
- the General Improvement Engine itself
- the Polishing specialization

## Constitutional immutability during campaign
The following cannot be silently modified by candidate generations:
- authoritative target contract
- evidence-state semantics
- permission/authority invariants
- hidden holdout boundary
- critical safety/integrity gates
- promotion authority
- rollback requirement
- benchmark identity already committed for the comparison

Changing these requires a separate explicitly authorized governance campaign, not an ordinary self-evolution candidate.

## Learning without benchmark gaming
After evaluation, Builder may receive bounded diagnostic summaries, failure classes and permitted evidence. Future hidden cases stay hidden. The system can learn mechanisms and failure patterns without receiving the answer key to future promotion tests.

## Anti-deception / evaluator robustness
Judge-of-Judge campaigns inject known-good, known-bad, deceptive, overfit and mutation-generated candidates. If evaluator behavior becomes unreliable, promotion pauses. Metric gains that conflict with semantic evidence trigger investigation rather than automatic acceptance.

## Mobile/resource rule
Self-Evolution is not an always-on Android background process. Heavy research, evaluation and recursive campaigns run only when explicitly scheduled/authorized and should use remote/host resources where appropriate. Device runtime keeps lightweight monitoring, evidence capture and safe local adaptation only within resource budgets.

## Rollback and survivability
Every executable promotion must bind:
- previous known-good version
- migration compatibility
- rollback path
- evidence bundle
- candidate hash/version
- affected dependencies
- revalidation set

A candidate that cannot be safely rolled back where rollback is required cannot be auto-promoted.

## Integration with V4.4 and Debugging Fabric
V4.4 Velocity Fabric optimizes evaluation topology and elapsed time without weakening proof. Debugging & Repair Fabric handles causal diagnosis and Repair Burst. Incremental ProofGraph invalidation determines what evidence must rerun after a repaired candidate.

## Evidence boundary
This integration is architecture-only. It does not claim Seven currently performs autonomous recursive self-evolution, hidden-holdout management, automatic promotion or rollback in runtime.

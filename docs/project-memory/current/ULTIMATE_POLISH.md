# Seven AI — Ultimate Polish Plan

> **Purpose:** Authoritative refinement campaign for the complete capability inventory in `CAPABILITY_REGISTRY.md`. This plan defines how systems are audited, challenged, accelerated, simplified, evaluated and frozen. It is not a blanket implementation claim.

## Prime Directive
For every canonical Seven capability and every Tool Fabric 2.0 capability, ask:

> What is the strongest practical version we can build while preserving truth, safety, recoverability, Android efficiency, maintainability, Unlimited Experience, speed, smoothness and a Zero-Manual Seven experience?

Polish strengthens systems. It does not reward random feature accumulation or expose internal complexity to the user.

## Maximum Work-Per-Message Execution Law 🔥
Ultimate Polish is executed in the largest safe, coherent Mega-Waves practical for the current task. Every development turn should accomplish as much verified work as reasonably possible instead of spending turns on ceremonial status checks, tiny patches or repeated requests to continue.

At the start of each subsequent Ultimate Polish development turn, re-read this section and use it as an execution constraint.

Default loop:
`Re-read current plan/status → take the largest safe coherent scope → inspect only evidence required to avoid blind changes → implement/polish the whole scope → run the strongest practical final verification → repair material failures in the same turn when practical → preserve evidence/status in GitHub → automatically advance as far as remaining turn/tool capacity safely allows.`

Rules:
- Target roughly 18–25 maximum-density Mega-Wave turns for the complete campaign when reality permits; this is an efficiency target, not a quality gate.
- Never split work merely to create another progress message.
- Do not stop after a PASS if another dependency-safe campaign can be advanced in the same turn.
- Prefer one large coherent patch plus meaningful final verification over many tiny patches/checks.
- Intermediate inspection is allowed when required to prevent corruption, resolve implementation truth, protect invariants or choose between materially different designs.
- Never trade correctness, evidence, rollback safety, Android constraints, Zero-Manual quality, Unlimited behavior, Speed or Smoothness merely to reduce turn count.
- If a tool, CI, permission boundary or unexpected failure blocks further safe progress, record the exact blocker and preserve completed work rather than fabricating completion.
- Architecture-only progress must remain labeled architecture-only; implementation PASS requires implementation evidence.

## Four Cross-Cutting Product Laws
Every Ultimate Polish campaign is governed by four product-wide laws. They apply to every capability, Tool Fabric 2.0 component, workspace and user flow.

### 1. Seven Unlimited Experience ♾️
Seven should not introduce arbitrary product-level usage quotas or artificial limits where they are not required for correctness, safety, device stability or external-resource reality. The user experience should feel open-ended across chat, projects, coding, research, RPG, memory, tools and reasoning.

Unlimited does **not** mean unbounded RAM, battery, storage, concurrency or background work. Seven should preserve the open-ended experience through pagination, lazy loading, tiered/persistent storage, context reconstruction, safe compaction, scheduling, routing, fallbacks and Resource Governor policies rather than by accumulating everything in memory.

For every capability ask:
- Is there an internal limit that provides no material safety/reliability/resource benefit?
- Can the limit become adaptive, virtualized, paginated, streamed or storage-backed instead?
- Can temporary resource scarcity be handled through routing/fallback/recovery rather than unnecessarily terminating the user's workflow?
- Does the capability remain stable during very long-lived use?

Unlimited is a product-experience principle, never a license to bypass external service rules or truthful resource constraints.

### 2. Seven Speeding System ⚡
Speed is the reduction of real waiting: startup, time-to-interactive, time-to-first-useful-result, tool/model/retrieval latency, completion latency and cancellation latency. Remove waste before removing capability and prioritize the user's critical path.

### 3. Seven Smoothness System 🌊
Smoothness is a first-class quality dimension independent from raw speed. A fast result delivered through freezes, jank, layout jumps, blocked input or confusing dead time is not polished.

Smoothness includes frame stability, non-blocking UI, natural streaming, immediate interaction feedback, progressive results, stable layouts, responsive cancellation, coherent transitions, background scheduling, animation governance and continuity between chat, tools and specialist workspaces.

**Fast but janky = FAIL. Smooth but unnecessarily slow = FAIL.**

### 4. Seven Zero-Manual Experience 🧭
The user should not need to understand Seven's architecture before receiving value.

> **Open → Ask → Seven figures out the appropriate path → Result.**

Capability complexity must not become user complexity. Documentation remains available, but ordinary successful use should not depend on reading it.

Zero-Manual includes:
- Intent First: natural-language goals before mode/configuration selection;
- Auto-Configuration: Seven chooses appropriate routing, tools, context and compute defaults when safe;
- Smart Defaults: strong defaults minimize setup and repetitive choices;
- Progressive Disclosure: advanced controls appear when useful rather than dominating first use;
- Just-in-Time Guidance: tiny contextual explanations at the moment they matter;
- Natural-Language Navigation: users can ask Seven to open, resume, search, build or change workflows;
- Actionable Empty States: empty surfaces teach through useful actions rather than documentation walls;
- Explain on Demand: users can inspect why a route/tool/action was chosen without making that explanation mandatory;
- Automatic Safe Recovery: failures offer understandable recovery rather than cryptic internal errors;
- Expert Escape Hatch: Zero-Manual never means Zero-Control; advanced users retain explicit controls;
- Learn Without Blocking: onboarding and What's New teach incrementally and remain skippable;
- Discoverability: powerful capabilities must be findable without memorizing product topology.

### Zero-Manual Golden Test
For every user-facing capability, test whether a new user with no Seven documentation can:
1. discover that the capability can help;
2. express the intended goal naturally;
3. start the correct workflow;
4. understand meaningful progress/state;
5. finish the task;
6. recover from a representative failure;
7. find advanced control only if desired.

If an ordinary task requires external documentation, knowledge of internal names such as Model Fabric/Tool Fabric/Context Workspace, or unnecessary configuration before first value, the capability fails this gate.

Track **Time-to-Value** from opening/entering the relevant surface to the first genuinely useful result, while preserving truth and correctness.

## Campaign Upgrade — Capability-Level Polish
The earlier 12 Boss Systems remain useful grouping containers, but they are no longer the smallest polish unit. **Every capability in `CAPABILITY_REGISTRY.md` receives its own dedicated campaign.** Tool Fabric 2.0 Waves 01–19 and their resulting contracts/brokers/capabilities are included.

For each capability:
1. reconstruct current architecture and implementation truth;
2. identify dependencies and invariants;
3. run Maximum Effort Polish Pass A;
4. run the Unlimited Gate;
5. run the Speed Gate;
6. run the Smoothness Gate;
7. run the Zero-Manual / Discoverability Gate where user-facing;
8. challenge the strengthened result adversarially;
9. run Maximum Effort Polish Pass B independently against the strengthened state;
10. allow `NO_MATERIAL_IMPROVEMENT` if evidence supports it;
11. run a Simplifier Duel against a materially simpler candidate where applicable;
12. define implementation/eval plan and freeze criteria;
13. preserve results in GitHub Project Memory.

Two passes mean two opportunities to discover material improvement, not two mandatory rewrites. Never add complexity merely to make Pass B look productive.

## Seven Speeding & Smoothness System ⚡🌊
This is a cross-cutting optimization layer applied to **every** capability rather than a final one-time performance pass.

Optimize cold/warm startup, time-to-interactive, time-to-first-useful-result, end-to-end and tail latency, frame stability, input/cancellation responsiveness, scheduling/concurrency, redundant model/tool/retrieval/verification work, context compilation, memory pressure, cache correctness, progressive/lazy loading, network/storage cost, background work, thermal/battery pressure and truthful perceived responsiveness.

### Speed & Smoothness Laws
- remove waste before removing capability;
- use cheap/direct paths before expensive escalation when valid;
- cache only with correct authority/freshness/identity boundaries;
- parallelize only independent work;
- cancel obsolete work aggressively when safe;
- prioritize critical-path work;
- defer optional heavy work;
- keep expensive/background work off the interaction-critical UI path where possible;
- provide immediate truthful feedback when useful work cannot complete instantly;
- prefer progressive useful output over dead waiting when correctness permits;
- performance tiers may reduce decoration/optional depth but not required correctness or safety;
- measure tail latency, jank, frame stability and perceived continuity, not only averages.

## Simplifier Duel
After strengthening a capability, compare it with the strongest materially simpler design that could preserve its required value and invariants. Prefer the simpler candidate when it achieves comparable correctness/value with meaningfully lower latency, memory, failure surface or maintenance cost. Complexity must earn its place.

## Integration Polish
Capabilities are not frozen solely from isolated success. Test important interfaces such as Memory ↔ Context, Context ↔ Model Routing, Models ↔ Tools, Tools ↔ Permissions/Verification, Coding ↔ Projects, Research ↔ Search, RPG ↔ Memory/State, Real Works ↔ Canon evidence and UX ↔ Resource Governor. Cross-system friction, duplicate work and hidden coupling count as polish failures.

## Maximum Effort Execution
Every substantial pass uses `MAXIMUM_EFFORT_PROTOCOL.md`. The command is generated for the exact capability and explicitly includes research, architecture, adversarial failure search, implementation reality, Unlimited behavior, mobile cost, speed, smoothness, Zero-Manual usability, verification, simplification and preservation.

The protocol itself can be polished when a material weakness is discovered. It is not a magic immutable prompt.

## Design Genome Rule
Seven must develop recognizable product DNA rather than copying another AI application or design system. Candidate primitives such as Orbit Thread, Seven Cut, Evidence Rail, Focus Halo and State Node are hypotheses until tested. Token governance and Design Lint prevent later UI from drifting outside the selected genome.

## Logo Tournament Rule
The final mark must survive small-size legibility, monochrome, Day/Night, adaptive masks, themed icons, splash/motion, distinctiveness and implementation/resource cost. Earlier logo concepts remain candidates/history until a winner earns freeze.

## Failure & Recovery Campaign
Challenge representative systems with network/provider failure, timeout, malformed tool/model output, corrupted/stale cache or state, interrupted writes, partial streaming, cancellation, permission denial, duplicate side-effect risk, low-memory/resource pressure and app restart. Seven should fail safely, preserve authoritative state, explain the problem in user language and recover automatically when safe. A user should not need a troubleshooting manual for routine recoverable failures.

## Seven Evals
Each applicable capability receives functionality, regression, latency/resource, smoothness, adversarial, integration and usability/discoverability evaluation. Project-wide suites should cover Coding, Research, Tools, Memory, Context, RPG continuity, Real Works canon fidelity, visual behavior and Android constraints.

Zero-Manual evaluation must include representative first-use tasks with no documentation supplied. Unlimited evaluation must include long-lived/high-volume scenarios while measuring bounded device-resource behavior.

## Self-Evolution Gate
Self-Evolution follows an evidence pipeline rather than self-promoting changes:

`Discover → Propose → Sandbox → Eval → Compare → Challenge → Approve → Canary → Promote`

A proposed evolution that does not materially improve the relevant objective under the project's invariants is rejected.

## Cross-Generation Protection Ratchet
A promoted generation must not silently regress protected dimensions such as correctness, reliability, speed, smoothness, bounded resource behavior, recovery, accessibility or required capability coverage. Improvements in one dimension do not excuse material regressions in protected dimensions without an explicit current decision.

## Freeze / Saturation Rule
A capability freezes only when its relevant architecture, behavior, failure modes, Unlimited behavior, speed, smoothness, Zero-Manual usability, performance, security/integrity, verification and UX gates are satisfied. Two consecutive valid challenge rounds with no material improvement may support saturation for the scope being tested. A material change to the constitution, implementation or evidence environment can reset that saturation.

Architecture saturation, implementation saturation and release saturation are distinct claims.

## Final Seven Red Team
Before release-level saturation, attack Seven as a complete product: security, hallucination/truth failures, state corruption/data loss, tool misuse, recovery failure, pathological slow paths, leaks/resource pressure, visual inconsistency, Android failure, accessibility/RTL, provider failure, malicious/malformed tool/file inputs, huge projects, long-lived Unlimited workflows and Zero-Manual first-use/recovery flows. Any material weakness routes back to the responsible capability or cross-cutting law.

## Updated Campaign Pipeline
`Truth Preflight → Speed + Smoothness Foundation → Capability Pass A → Unlimited Gate → Speed Gate → Smoothness Gate → Zero-Manual/Discoverability Gate → Adversarial Challenge → Pass B → Simplifier Duel → Integration Polish → Specialist Campaigns → Failure & Recovery → Seven Evals → Android/Resource Verification → Final Red Team → Saturation 2/2`

## Campaign Order
Use dependency-aware ordering rather than blindly walking a numbered list. Establish Speed + Smoothness foundations early, then prioritize upstream foundations (Cognitive Runtime, Truth, Memory, Context, Models, Tool Fabric, Verification/Evals) before dependent specialist surfaces (Coding, Research, RPG/Real Works) where that prevents rework. Visual implementation continues through its 12 Mega-Waves and must integrate the four cross-cutting laws rather than becoming a separate decorative track.

## Completion Truth
Ultimate Polish is complete only when capability-level records, implementation truth and evaluation evidence support completion. A strong plan is not implementation; an implemented feature is not verified release quality; and a visually impressive result is not proof of correctness.

The target experience is deliberately simple despite Seven's internal depth:

> **Unlimited where practical. Fast. Smooth. Zero-Manual. Powerful underneath, obvious on the surface.**

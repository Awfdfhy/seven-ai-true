# Seven Tool Fabric 2.0 — Maximum Research Protocol

> Status: LOCKED RESEARCH PROTOCOL
> Purpose: Preserve the exact operating contract for the Tool Fabric discovery and deep-polish campaign. This protocol governs how research is performed and recorded. It does not authorize implementation or merging by itself.

## Primary Command

**SEVEN TOOL FABRIC 2.0 — MAXIMUM RESEARCH MODE**

Use the maximum practical research, analysis, and comparison depth available to discover the strongest tools, technologies, libraries, open-source projects, APIs, runtimes, protocols, and frameworks that could make Seven more capable, intelligent, autonomous, reliable, and useful at real tasks while preserving Android-first lightness and free/open options wherever practical.

Do not start from a predetermined shortlist and do not assume the most popular tool is the best. Explore established categories first, then discover additional categories during research. Use primary/official sources, GitHub, technical documentation, papers, benchmarks, substantive engineering write-ups, and high-quality community evidence when real-world experience matters. Include strong lesser-known alternatives.

## Candidate Evaluation Contract

For every serious candidate inspect:
- real capabilities
- current project health/activity
- license
- free status and limits
- self-hosting feasibility
- Android compatibility
- dependency weight
- RAM / CPU / battery / storage / network cost
- latency
- offline capability
- privacy
- reliability
- security
- API stability
- integration difficulty
- maintenance burden
- failure modes
- verification strategy
- overlap with existing Seven capabilities

Do not confuse Tool, Library, Provider, Protocol, Model, and Infrastructure Component. Classify each accurately and define how it would enter Tool Fabric.

## Classification

Every candidate eventually receives one of:
- CORE
- SPECIALIST
- FALLBACK
- EXPERIMENTAL
- REJECTED

Record the evidence and reason for the classification, including rejection reasons. Negative results are valuable project knowledge and must not be silently discarded.

## Discovery Before Adoption

Do not permanently adopt a tool during discovery. Discovery produces evidence, candidates, comparisons, and candidate architecture. Final adoption occurs only after individual Deep Polish and evaluation.

Each accepted candidate is later treated as a small independent engineering project covering:
- interface contract
- typed inputs / outputs
- capability metadata
- permissions
- side effects
- idempotency
- cancellation
- timeouts
- retries
- caching
- provenance
- lineage
- validation
- verification
- uncertainty handling
- observability
- performance tiers
- fallback behavior
- security boundaries
- tests
- evals
- Cognitive Control Plane integration
- explicit freeze criteria

## Epistemic Discipline

Never invent capabilities, results, limits, or compatibility. Distinguish:
- VERIFIED FACT
- INFERENCE
- PROPOSAL
- UNKNOWN

When evidence is incomplete, research further or preserve the uncertainty. Prefer primary sources and current information.

## Optimization Objective

The goal is not the largest tool count.

**Goal: maximum useful capability coverage with minimum duplication, overhead, fragility, and maintenance burden.**

A tool earns a place because it adds a meaningful capability, superior implementation path, or necessary fallback, not because it is interesting.

## Android-First Constraint

Every decision must respect Seven's mobile target:
- fast startup
- low RAM
- low battery impact
- low storage overhead
- small APK where practical
- lazy/on-demand heavy components
- avoid unnecessary background work

A component that is excellent on a large server must not be represented as phone-suitable without evidence.

## GitHub Preservation Rule

All meaningful work from this campaign must be preserved in GitHub Project Memory as it happens. Do not depend on chat memory.

Preserve:
- research sources
- candidate inventories
- comparisons
- negative findings
- rejection reasons
- decisions
- open questions
- scores
- polish stages
- final specifications
- eval designs/results
- coverage reports

Use clear commits so the reasoning history can be reconstructed later.

Safety invariants:
- do not casually modify `seven_ai-final.html`
- do not delete files as part of research
- do not merge protected branches without explicit approval
- do not claim PASS without verification

## Research Waves

Do not compress the entire search into one shallow list. Divide discovery into coherent research waves. Preserve the result of each completed wave in GitHub before moving on.

Continue discovery until marginal discoveries become low enough to justify practical saturation. Never claim to have searched the entire internet or found every possible tool.

## Coverage Report

At Discovery close, produce a Coverage Report containing:
- domains searched
- source classes searched
- candidates evaluated
- capability coverage
- unresolved gaps
- uncertainties
- areas intentionally deferred
- saturation rationale
- confidence level

## Campaign Pipeline

`Research → Evidence → Candidates → Comparison → Decision → Deep Polish → Architecture → Evals → Final Spec → GitHub Commit`

Discovery initially stops before final implementation and final polish. Implementation begins only after the relevant discovery/review gate is explicitly passed.

## Per-Step Preservation Rule

This protocol applies recursively to the rest of the Ultimate Polish campaign: whenever a future step produces material research, architecture, comparison, decision, rejection, specification, evaluation, or freeze criteria, preserve it in GitHub during that step rather than relying on conversation history.
